# M100 Bot — контекст проекта

Тестовое задание на вакансию AI-разработчика. Прототип Telegram-бота: мастер на стройке
присылает дневной отчёт в свободной форме (текст или голос), бот распознаёт работы и объёмы,
сопоставляет их с позициями сметы, показывает список на подтверждение и после подтверждения
пишет объёмы в Google-таблицу и в Битрикс24.

Оригинал задания: `../Тестовое задание AI-разработчик.pdf`. Образец таблицы: `tests/fixtures/sample.xlsx`.

## Главные правила (не нарушать)

1. **Ничего не записывать без явного подтверждения мастера.** Запись в Sheets/Битрикс — только из
   обработчика кнопки «✅ Записать».
2. **Не угадывать.** Если позиция не найдена или подходят несколько, бот спрашивает (кнопки с
   вариантами). Лучше лишний вопрос, чем объём не в той строке.
3. **Справочник позиций читается из таблицы**, в коде позиции не хардкодим. Синонимы мастера живут
   на отдельном листе «Синонимы» той же таблицы.
4. **Эталонный набор `tests/golden/phrases.yaml` — источник истины.** Не менять `expected`, чтобы
   тест прошёл. Если считаешь, что эталон неверен, — остановись и спроси.
5. Секреты только в `.env`, никогда не коммитить. `.env.example` держать актуальным.

## Структура таблицы (лист «Лист1»)

- Строки 1–2: шапка (объединённые ячейки). Колонки:
  A `№`, B «Наименование по спецификации», C «ед изм», D «к-во» (по смете), E «ЗП за ед.»,
  F «ЗП на руки итого» (`=E*D`), G «Остаток объема» (**пустой, формулы нет** — остаток считаем
  в коде как `D − I`), H «Выполнено в деньгах» (`=I*E`), I «Выполненный объем» (`=SUM(J:CZ)`).
- Строка 3: даты рабочих дней, начиная с колонки J. Строка 4: под каждой датой слово «объем».
- Данные с 5-й строки. Ячейка (позиция × дата) = объём за день; пустые ячейки — норма.
- **Не каждая строка — позиция.** Бывают:
  - разделы: «ОВ 3» (B4), «ЭМ3» (B53);
  - подзаголовки групп без ед. изм. и к-ва: «Материалы для сист К1-К7», «Дренаж системы К1…К7»,
    «Крепежные материалы…»;
  - итоги: «ИТОГО ПО ОВ 3», «ИТОГО ПО ЭМ3», «Всего за август».
  Позиция = строка, где заполнены и ед. изм., и к-во.
- Ловушки в данных:
  - даты с пропусками и **дубликатами** (30.09 в AV3 и AW3) — искать столбец по значению даты;
    при дубликате писать в первый и логировать предупреждение;
  - `SUM(J:CZ)` — новый столбец правее CZ не попадёт в итог; при создании столбца проверять это;
  - OCR-мусор в названиях («Tpyбoпpoвод», «omвepcmuй») — латиница вперемешку с кириллицей;
  - ед. изм. «М» и «м», десятичные «6,35» и «12.7»;
  - строки 48 и 49 с **одинаковым названием** «Сберление отверстий Д80» (к-во 18 и 26);
  - строки 10 и 15 — одна и та же модель MDSAI2-07HRFN8 в разных системах (К6 и К8);
  - короб ПВХ 25х16 (строка 67) считается в **шт** (по 2 м), а мастер может сказать в метрах.
- Строку позиции идентифицируем по номеру строки листа (`row`); при загрузке справочника
  дополнительно сохраняем № из колонки A и название, чтобы ловить сдвиг строк.

## Архитектура

```
src/m100bot/
  config.py            pydantic-settings, всё из .env
  __main__.py          точка входа: python -m m100bot
  sheets/catalog.py    парсинг справочника и столбцов дат из «сырых» строк (без сети) ✅ готово
  sheets/addressing.py  адреса ячеек, план столбца даты, формулы SUM, запросы batchUpdate ✅ готово
  sheets/client.py     gspread: чтение листа, поиск/создание столбца даты, batch-запись ✅ готово
                       (проверено на имитации; на живой таблице — scripts/try_sheets.py)
  matching/normalize.py нормализация текста и чисел ✅ готово
  matching/features.py  признаки из названий: диаметр, сечение, ток, размер, модель ✅ готово
  matching/llm.py       вызов LLM (локальная Ollama, JSON-схема) → черновые позиции
  matching/matcher.py   гибрид: синонимы → LLM → валидатор признаков/ед. изм. → статус
  matching/models.py    pydantic-модели результата
  bitrix/client.py      вебхук Битрикс24, retry; upsert элемента смарт-процесса ✅ готово
                        (поля ищутся по названию; живая проверка — scripts/try_bitrix.py)
  voice/transcribe.py   голос → текст: Whisper через Groq (OpenAI-совместимый API) ✅ готово
  storage/db.py         SQLite: черновики, журнал записей, outbox для Битрикса ✅ готово
  services/report.py    сценарий: распознать → подтвердить → записать → журнал ✅ готово
                        (Битрикс — через outbox: flush_outbox() сразу после записи в фоне,
                        повторы — фоновой задачей раз в минуту из __main__)
  bot/                  aiogram 3 ✅ готово: handlers (сценарий), render (тексты), keyboards,
                        access (ALLOWED_USER_IDS), states (только режимы ввода), app (сборка)
```

Поток данных: сообщение → (голос → текст) → `matcher.match()` → черновик в SQLite → карточка
с кнопками (Записать / Исправить / Удалить / Добавить) → при неоднозначности кнопки выбора →
подтверждение → Sheets (batch) → журнал → Битрикс (через outbox, с повторами) → кнопка
«Открыть таблицу».

### Сопоставление (самая важная часть, оценивается в первую очередь)

1. Нормализация фразы (`normalize.py`).
2. Точное совпадение по листу «Синонимы» → позиция найдена без LLM.
3. LLM получает весь справочник (≈65 позиций, `row | название | ед.`) и фразу; возвращает JSON:
   для каждого упоминания — `phrase, qty, unit, kind, features, candidates[row]`.
   Ссылки вида «изоляцию на них столько же» LLM раскрывает в отдельные позиции.
4. Валидатор в коде: признаки из фразы (диаметр 6,35 / сечение 3х2,5 / ток 16А) должны совпасть
   с признаками кандидата из `features.py`; ед. изм. должна совпасть. Остался один кандидат →
   `ok`; несколько → `ambiguous`; ноль → `not_found`; ед. изм. не та или объём не назван → `clarify`.
5. Лист «Синонимы» ведёт только человек (администратор); бот его читает, но не пишет.

Согласованные правила (2026-11-02, отражены в шапке `phrases.yaml`):

- Объём не назван: единственное число + позиция в «шт» → 1; иначе → `clarify`.
- Любая названная работа вне сметы → `not_found` (в т.ч. «вынесли мусор»).
- Пишем только в названную строку: материал → строка материала, работа → строка работы.
  Строки работ 68–71 (установка АВ, прокладка кабеля) автоматически не дописываем.
- Размер без материала («шестёрка», «девятка») → `ambiguous` по всем позициям с этим размером.
- Кнопки выбора для строк с одинаковыми названиями (48/49) должны различаться (к-во по смете, № из A).
- Названия позиций в карточке — полные (`Position.short_name`), короткие автоматически не строим.
- (2026-11-03, отменяет прежнее автообучение) Бот синонимы не пишет: один выбор кнопкой
  закреплял общее слово («гофру» → хомут, «хомутов» → 43) и ломал правило «не угадывать».
  Лист «Синонимы» ведёт человек, только для однозначных фраз.
- (2026-11-03) Жаргон, однозначно называющий материал («гофра» = труба ПВХ), продублирован
  в коде (`phrase.JARGON` → слова из названий, не номера строк): модель 8B правило из промпта
  соблюдает ненадёжно. Позиции для такой фразы берутся по названию, а не из ответа модели.
- Состояние сценария — в черновике (SQLite), не в памяти; от старых кнопок защищает
  `Draft.token` в `callback_data`.
- (2026-11-03) Новое сообщение при незаписанном отчёте **дописывается** в него, если черновик
  сегодняшний; про вчерашний бот спрашивает («Добавить к нему» / «Новый отчёт»). Молча стирать
  черновик нельзя.
- (2026-11-03) «Сколько осталось по …» — `intent: question` в ответе LLM; сообщение с объёмом
  сделанной работы — всегда отчёт (проверка в коде). Вопрос не трогает черновик и режим.
- (2026-11-03) Объём, которого нет в тексте мастера (ни цифрами, ни словами, кроме правила
  «1 шт»), код не принимает от LLM → `clarify`. Повтор одного упоминания 3+ раз подряд —
  «зацикливание», схлопывается; ровно MAX_MENTIONS (15) упоминаний — мастер получает ⚠️.
- (2026-11-03) Вопрос «какой вариант?»: полные названия — нумерованным списком в тексте,
  на кнопках только номера (длинный текст кнопки Telegram обрезает).

### LLM: локальная модель через Ollama

Облачные API из Беларуси недоступны для оплаты физлицом, поэтому основная LLM — локальная.
- Ollama отдаёт OpenAI-совместимый API на `http://localhost:11434/v1`, код клиента тот же (`openai`).
- **Контекст.** По умолчанию у Ollama окно 4096 токенов, а справочник + промпт ≈ 5 тыс. — лишнее
  молча обрезается и модель «не видит» часть позиций. На машине задана переменная
  `OLLAMA_CONTEXT_LENGTH=8192`; в коде при старте проверять длину промпта и логировать её.
- **Компактный справочник** в промпте: `строка | короткое название | ед.` — меньше токенов,
  быстрее ответ на CPU.
- **JSON.** Передавать `response_format` с JSON-схемой из `LlmResponse`; ответ всё равно
  валидировать pydantic и при ошибке делать 1 повтор.
- **Qwen3 «думает»** перед ответом — это медленно. Для извлечения рассуждения не нужны:
  отключать thinking (через параметр Ollama или `/no_think` в промпте — проверить, что работает).
- **temperature=0**, таймаут из `LLM_TIMEOUT_S`.
- **Резерв:** если заданы `LLM_FALLBACK_*`, при недоступности Ollama запрос уходит туда.
- Бот работает, только пока включён компьютер с Ollama, — это ограничение прототипа, указать в README.

### Семантика записи

Реализация (`services/report.py`): ошибка Sheets не стирает черновик — `ReportError` с текстом
для мастера; неразобранные позиции после «Записать» остаются в черновике; в Битрикс уходит
каждый подтверждённый отчёт отдельным элементом «Отчет от <дата время>» (id элемента хранится в
таблице `reports`); исправление обновляет элементы отчётов, где была позиция
(`distribute_correction`: прибавка — в последний, уменьшение — с последнего назад).

- Новый отчёт за сегодня **прибавляет** объём к значению в ячейке.
- «Исправить сегодняшнее» задаёт новый **итог этого мастера** по строке: в ячейку пишется
  разница к его итогу по журналу (режим `delta`), чужие объёмы остаются (2026-11-03).
- Перед записью — «намерение» в SQLite (`pending_writes`), закрывается в одной транзакции с
  журналом; повтор после сбоя идёт через `resume_write` и не удваивает. Пока намерение
  открыто, черновик не меняется (2026-11-03).
- Сдвиг строк сверяется с отпечатком позиции в черновике (`MatchedItem.pos_number/pos_name`),
  а не со справочником в памяти: тот перечитывается перед записью (2026-11-03).
- Дата записи — день отчёта (`drafts.work_date`, первое сообщение), а не день нажатия
  «Записать» (решение пользователя 2026-11-03). Кнопки /today несут дату (`Today.d`).
- «Дописать или новый» для обычного сообщения решает `recognize(append=None)` под блокировкой.
- Нечитаемый после обновления черновик удаляется с сообщением мастеру (`DraftLostError`).
- Перед подтверждением: предупреждение ⚠️, если объём > остатка (`D − I`).

## Соглашения

- Python 3.12, типизация везде, pydantic v2 для моделей, async (aiogram/httpx).
- Модули без сети (`catalog`, `normalize`, `features`, валидатор) — чистые функции, покрыты тестами.
- Внешние вызовы (Sheets, Битрикс, LLM, Whisper) — через тонкие клиенты с `tenacity`-повторами
  и понятной ошибкой для мастера («Таблица недоступна, отчёт сохранён, повторю через минуту»).
- Тексты бота — короткие, на «ты» не переходить, эмодзи только как маркеры статуса (✅ ⚠️ ❓).
- Логи — loguru; не логировать токены и полные URL вебхуков.

## Открытые вопросы (уточнить у работодателя, решение записать в README)

  «Прокладка силовых кабелей в трубе» (69)? В образце данные стоят только в строке кабеля —
  пока пишем только туда. Так же для автоматов и строки 68 «Установка АВ на DIN-рейку».

  (46) и под дренаж (47) — значит ли 48 = фреон, 49 = дренаж? В образце сверление в дни установки
  дренажных гильз записано в 48. Пока бот спрашивает.
- Что именно создавать в Битрикс24: сделан элемент смарт-процесса «Дневной отчёт» на каждый
  подтверждённый отчёт (решение пользователя 2026-11-03). Уточнить, устраивает ли это работодателя.
